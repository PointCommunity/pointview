PointView development pipeline

PointView uses one governed Issue from Backlog through verified Production. The agent owns deterministic Project movement and delivery work; the human Project Manager selects work and approves the exact Production candidate.

Lifecycle

Backlog
Open, unassigned, complete metadata.
In Progress
One active Issue, assigned to brimdor, Issue branch.
Agent review
Tests, security, browser QA, CI, remediation.
Canary
Exact head, immutable Zot digest, Argo deployment.
In Review
PM tests the recorded live candidate.
Production
Approved tree, same digest, verification, cleanup, Done.

Agent-owned Project movement

The agent reads, changes, and immediately reads back Status and metadata. The PM never has to drag a card. Exactly one Issue may be in In Progress or In Review. Backlog Issues are open and unassigned; the active Issue is assigned only to brimdor.

Issue and pull-request contract

  • New work requires a complete approved HTML Issue body and metadata before creation.
  • Every open Issue is in the private PointView Project with Status, Priority, Impact, Effort, exactly one type:* label, and at least one area:* label.
  • Branches use issue/<number>-<slug>. Pull requests target main, contain Refs #N, and never use an auto-close keyword.
  • An open PR does not justify In Review. Complete QA, exact CI, live Canary, and whole-cluster health are required first.

Feedback-triage boundary

PointView's runtime may create a new Backlog Issue or add one privacy-minimized comment to a non-Done Issue. Those operations do not take the active development slot and never change development Status. Runtime triage cannot assign implementation, create branches or pull requests, invoke repository lifecycle skills, merge, deploy, close, or set Done. Only the PM starts development through the target repository's own pipeline.

Quality and Canary

  1. Implement test-first in small vertical slices and preserve unrelated work.
  2. Run focused tests while iterating, then npm run check, browser/accessibility tests, security checks, production build, migration rehearsal, dependency audit, and git diff --check.
  3. Require successful GitHub Quality / verify and Container / amd64 for the exact PR head.
  4. Build from a clean committed archive on the local workstation for linux/amd64. Never build on Kubernetes nodes.
  5. Push once to Zot, resolve the registry digest, and pin the immutable digest in apps/pointview-canary.
  6. Check the latest stable version published by the official bjw-s chart repository, review upgrade notes, and inspect rendered changes before adoption.
  7. Deploy only through the canonical Gitea-backed homelab GitOps repository and Argo CD. Verify source SHA, digest, migrations, web, triage/retention Jobs, storage, Access, and whole-cluster health.

Production lock

Production requires the exact phrase Approved to merge and deploy production for the recorded Issue, PR head/tree, Zot digest, chart generation, and Canary homelab revision. Any candidate change invalidates approval.

After approval, prove tree equality, squash-merge, wait for required merge-result checks, and promote the identical Canary digest to apps/pointview without rebuilding. No second approval or pause occurs. Keep the Issue open and In Review until Production and the whole cluster are green.

Homelab data is critical. Verify PVC/PV identity, reclaim policies, current configuration, backup freshness/restorability, migration compatibility, and non-destructive rollback before Production mutation. Destructive data restoration requires new PM authorization.

After successful verification, the Production workflow purges obsolete unreferenced PointView image manifests from Zot and proves the retained Production digest remains pullable. It does not wait for Zot's delayed background garbage collection. Only then close the Issue and set Done.

Skill ownership

  • pointview-create-issue: draft and approved Backlog creation.
  • pointview-audit-issues: Backlog-only metadata audit.
  • pointview-work-issue: selection, active slot, implementation, PR.
  • pointview-review-issue: full QA, remediation, Canary, In Review.
  • pointview-release-canary: immutable packaging and Canary verification.
  • pointview-close-issue and pointview-release-production: exact approval, merge, Production, cleanup, closure.
  • pointview-pipeline-health: read-only drift/health audit.
  • pointview-maintain-skills: governance maintenance.
