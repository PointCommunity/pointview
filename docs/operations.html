Daily schedule

The Kubernetes triage CronJob runs once daily with concurrency policy Forbid. The Job invokes container mode triage; PostgreSQL is the final singleton authority. It leases exactly one oldest eligible record and continues sequentially until the queue is empty.

The retention CronJob invokes retention separately. Neither Job starts development work in a target repository.

Pause and requeue

  • Only an Owner may pause or resume global triage. A pause reason is mandatory and versioned.
  • Admins may annotate records and requeue eligible Needs Attention records; each requeue creates a new decision generation.
  • Never edit lease or decision tables manually. Do not delete an operation marker to force a GitHub retry.
  • Rate-limit responses are honored. A global integration failure may stop drainage to prevent unsafe writes.

Deploy and promote

  1. Run source, migration, security, browser, accessibility, and container gates on one clean commit.
  2. Build once for linux/amd64 and publish the immutable image to Zot.
  3. Pin its digest in the isolated Canary GitOps app and verify UI, API, Jobs, storage, digest, and whole-cluster health.
  4. Keep the pull request open and Issue In Review during human Canary review.
  5. Only the exact approved candidate may be merged and promoted to Production, using the same digest without rebuilding.

Migration and rollback

Run container mode migrate as an explicit pre-deploy Job. Migrations must be forward-compatible with the currently running image during rollout. Before Production, verify database backup freshness and restore evidence, PVC identities and reclaim policies, the current digest/configuration, and a non-destructive GitOps rollback commit.

Rollback application configuration through Gitea and Argo. Never restore or delete data without explicit human authorization.

Incident order

  1. Pause triage if continued writes may be unsafe.
  2. Preserve Job, pod, database, GitHub request, operation, and audit identifiers without copying secrets or raw feedback.
  3. Classify record-local versus global failure.
  4. Repair durable configuration or code through the governed repository pipeline.
  5. Resume and verify oldest-first drainage, idempotent readback, and whole-cluster health.

Operational mutations flow through Git, Gitea, Argo CD, and the repository’s PointView lifecycle skills.
