PointView system guide

Architecture

A private contextual-feedback intake and evidence-bound GitHub Issue triage system. PointView makes triage decisions; it never starts development work.

Trust boundaries

Source application

Its backend signs short-lived, one-use Ed25519 launch assertions. Browser query strings and referrers are never trusted as provenance.

PointView

Cloudflare Access authenticates identity. PostgreSQL authorizes accounts and owns queue, lease, decision, operation, and audit state.

External services

Repository-scoped GitHub App credentials and encrypted model-provider credentials are server-only. Owners may connect Ollama Cloud, ChatGPT/Codex, or both; the model receives bounded evidence and no mutation credentials.

Processing flow

  1. A source backend signs context and POSTs the assertion to /launch.
  2. PointView validates origin, issuer, audience, expiry, key, nonce, registration version, and return path before creating a token-free session.
  3. An approved user submits text and up to five normalized screenshots. The database stores a queued record; no model call occurs during intake.
  4. The daily CronJob takes the PostgreSQL singleton batch lock and leases the oldest eligible record.
  5. Deterministic research captures every Project Issue, open pull requests, relevant repository evidence, and provider-hosted web results. Done Issues remain history only.
  6. The selected Ollama Cloud or ChatGPT/Codex model proposes split units and dispositions. Ollama output gets one bounded repair attempt; both paths must pass the same deterministic schema, evidence, target, label, field, and action validation.
  7. A risk review runs when required. Application code applies only MERGED, CREATED, or CONSIDERED, then verifies exact GitHub readback.
  8. The worker releases the lease and continues one record at a time until empty or a recorded global blocker occurs.

Authority ceiling

The automated triage runtime cannot assign implementation, change development status, create branches or pull requests, merge, deploy, close Issues, or set Done. A human Project Manager separately triggers each target app’s development pipeline.

Failure and recovery

  • Database uniqueness enforces one active batch and one active lease globally.
  • Expired leases can be recovered without reordering the queue.
  • Stable GitHub markers and an operation ledger recover lost responses without duplicate comments or Issues.
  • Record-specific exhausted failures become Needs Attention and do not strand later records.
  • Canary and Production have separate URLs, databases, volumes, secrets, and Argo applications.
