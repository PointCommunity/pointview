PointView threat model

PointView is an Access-protected homelab application that accepts confidential product feedback and optional screenshots, uses a model to organize evidence, and can create or enrich GitHub Issues. It is not intended to receive payment-card, health, or other regulated records.

Scope and assumptions

  • Confirmed: users are authenticated through Cloudflare Access and approved in PointView.
  • Confirmed: submissions may contain confidential product material and incidental personal information, but regulated records are prohibited.
  • Confirmed: initial mutation targets are selected repositories and private Projects in the PointCommunity GitHub organization.
  • Confirmed: Canary and Production are distinct homelab Kubernetes applications with separate data, storage, secrets, and domains.
  • Out of scope: attacks requiring control of Cloudflare, GitHub, OpenAI, 1Password, or cluster administration are supply-chain/administrator compromise scenarios; PointView still limits blast radius through least privilege and immutable evidence.

Trust boundaries

  1. User browser → Cloudflare Access → PointView: HTTPS, edge authentication, PointView session, CSRF/origin checks, application rate limits, resource authorization.
  2. Source-app backend → browser → /launch: form POST carrying a short-lived EdDSA JWS; issuer/audience/time/key/origin/return URL validation and transactional nonce consumption.
  3. Browser → upload decoder → private storage: multipart limits, magic/decode/dimension/pixel validation, re-encoding, generated keys, private retrieval.
  4. Web/Job process → PostgreSQL: TLS/private network, least-privilege database role, parameterized queries, constraints, advisory lock, append-only audit.
  5. Triage collector → GitHub: allowlisted repository/Project, short-lived GitHub App installation token, paginated reads, bounded writes, rate-limit handling.
  6. Evidence packet → OpenAI Responses API: redacted bounded evidence, strict schema, store:false, hosted web search only, no PointView credentials or mutation tools.
  7. Release workstation → Zot → Gitea/Argo → cluster: clean committed source, immutable AMD64 digest, exact-candidate promotion and readback.

Assets and entry points

High-value assets

  • Raw feedback and normalized screenshots
  • Source provenance and routing
  • GitHub App and provider secret references
  • Issue/Project integrity
  • Decision and audit lineage
  • Release image and GitOps identity

Untrusted entry points

  • POST /launch
  • Feedback multipart form
  • Record and attachment identifiers
  • Admin JSON mutations
  • GitHub Issues, PRs, repository content
  • Web-search results and model output
  • Job environment/configuration and external API responses

Security verification focus

  • Negative authorization tests for every record, attachment, administrative function, and GitHub target.
  • Adversarial corpus covering JWS replay/routing, upload polyglots and bombs, prompt injection, unsupported citations, unsafe HTML, and log injection.
  • Fault injection at each GitHub operation boundary and concurrent/expired Job execution.
  • Secret scanning of source, history, build context, layers, logs, fixtures, and generated evidence.
  • Canary egress, identity, storage isolation, retention deletion, immutable digest, rollback, and whole-cluster checks.

Residual risks

Model judgment can still be wrong despite validation; ambiguous cases therefore resolve to Considered or Needs Attention, and a second review is required for defined risk triggers. Approved operators can view sensitive raw submissions during the retention window; access logging, least privilege, and periodic role review remain operational responsibilities. Compromise of a trusted platform or administrator is not eliminated, but repository selection, short-lived credentials, isolated environments, immutable provenance, and restricted egress reduce blast radius.
